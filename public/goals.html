About GitHub Pulse

GitHub Pulse is one project with two layers. This tab is the data pipeline: every day it collects public activity from GitHub, cleans it, and organises it into tables. The AI Backend tab is the assistant on top: you ask questions in plain English, and each answer streams back with links to its sources.

DataGH Archive, a free public record of GitHub events. Nothing from EY and nothing confidential.
Why bothThe pipeline fills the gaps in your resume (Docker, AWS, CI, orchestration, data modeling). The AI layer is what AI backend roles ask for. Together they show you can build and run the whole thing.
Interview line"I built an end-to-end pipeline on AWS that processes GitHub events, and an AI backend on top with streaming answers, caching, a job queue and a measured accuracy."
Pipeline stages
  1. Set up (weeks 1-2). Create the repo. Run Postgres in Docker. Download 3 to 6 hourly files from GH Archive, load them into a table and write 5 SQL queries.Done when the queries return sensible results and are saved in /sql.
  2. Model it (week 3). Design a star schema: one fact table for events plus tables for repo, actor, date and event type.Done when the fact table has the same row count as the raw table.
  3. Package it (week 4). Turn your loading code into a small Python ETL in Docker, add tests and a CI workflow.Done when GitHub Actions shows a green check.
  4. Move to the cloud (weeks 5-6). Create an AWS account safely and write a script that uploads raw files to S3.Done when 7 hourly files sit in S3 and your budget alert is on.
  5. Schedule it (weeks 7-8). Wrap the download-and-upload in an Airflow DAG with retries.Done when it runs on a schedule and recovers after a forced failure.
  6. Clean it at scale (weeks 9-10). Use PySpark to clean, type and de-duplicate events, write Parquet partitioned by date, and query it in Athena.Done when the Athena row count matches Spark.
  7. Model it for analytics (weeks 11-12). Build dbt models for the star schema and a daily trending-repos table, with tests.Done when dbt build passes and you have a lineage graph screenshot.
  8. Document it (week 14). Draw the full architecture and write the README results section.Done when the README has a diagram, real numbers and a how-to-run section.

If you fall behind, finish stages 1 to 5 first. The AI layer needs the data in Postgres from stage 1 and the gold tables from stage 7.

Keep it small, cheap and clean
SizeGH Archive hourly files can be large. Check a file's size before downloading it. Take one hour per day, and keep only three event types early on: WatchEvent (stars), IssuesEvent and IssueCommentEvent.
CostSet an AWS budget alert first. Stop or delete databases and Glue jobs you are not using.
PrivacyEvents contain public usernames. Do not store emails or other personal details, and show aggregated results in your demo.
SecretsKeep AWS keys and API keys in environment variables. Never commit them to the repo.

Words you will meet
PipelineA chain of steps that moves data from a source to a place where people can use it.
IdempotentRunning a step twice gives the same result as running it once. It makes reruns safe.
ParquetA compact file format for tables. Queries read only the columns they need.
PartitionSplitting data into folders, such as one per date, so queries skip what they do not need.
DAGThe Airflow name for a pipeline: tasks and the order they run in.
EmbeddingA list of numbers that represents the meaning of a piece of text. Similar texts get similar numbers.
RAGFind the most relevant text first, then give it to the model so its answer is based on real sources.
EvalA fixed set of questions with known answers that you re-run to measure quality.

Why this track

An AI backend engineer builds the server side of AI products: calls models reliably, gives them the right data, returns validated JSON, streams answers, caches, runs background jobs, and measures quality and cost. It is backend work with an AI layer, so your Node, TypeScript, Postgres and pipeline experience carry over directly.

Your edgeAn XBRL data pipeline at EY (265K+ filings, validation and data-quality work) and WhisprLive (real-time sockets, auth, rate limiting, caching).
Gaps to closeDocker, AWS, CI, Redis, job queues, FastAPI, LLM APIs, evaluation. The Pulse project and this tab cover all of them.
Python or TypeScriptBuild the main app in Python, since most AI tooling is Python first. Use TypeScript for the React page and, if you like, the queue (BullMQ). Having both is an advantage.
Job titlesSearch AI Engineer, Applied AI Engineer, LLM Engineer, Backend Engineer (AI), Software Engineer (Python) and Data Engineer. Titles vary a lot between companies.
Keep EY outUse only public data and fresh code. Do not reuse company code or client data.
AI Backend stages
  1. Call a model (weeks 5-6). Use an LLM API from Python and TypeScript. Get validated JSON with Pydantic or Zod. Let the model call one of your functions.Done when a tool-use loop works and 95 percent of 50 issues return valid JSON.
  2. Make text searchable (weeks 7-8). Chunk issue text, create embeddings and store them in pgvector with an index.Done when search returns sensible top-5 results for 10 test questions.
  3. Serve it (weeks 9-10). Learn FastAPI, then build a streaming endpoint with Server-Sent Events.Done when curl -N shows the answer arriving in pieces, then the sources.
  4. Cache and queue (week 11). Add Redis for repeated questions and a background worker that embeds new issues.Done when a repeated question skips the model and POST /ingest returns a job id at once.
  5. Measure it (weeks 12-14). Write 20 golden questions, an eval script, and a before-and-after improvement. Trace every request with Langfuse.Done when the README shows real numbers, cost per question and a trace screenshot.
  6. Make it an agent (week 13). Build the /ask tool-use loop that chooses between a SQL tool and vector search.Done when answers include source links and match your schema.
  7. Ship it (weeks 15-16). Build the React chat page and deploy the API and the page on AWS. Record a demo.Done when a public URL works on your phone and the video link is in the README.

If you fall behind, finish stages 1 to 4 first. A streaming, cached RAG backend is already a strong project. Add the agent and the polish after.

Words you will meet
Structured outputThe model returns JSON that matches a schema you defined, so your code can rely on it.
Tool useThe model asks to run one of your functions. You run it and send the result back. Also called function calling.
ChunkingSplitting long text into small pieces so each piece can be embedded and retrieved on its own.
Hit rate at kHow often the right source appears in the top k search results.
SSEServer-Sent Events. The server keeps one HTTP response open and sends pieces as they are ready.
Cache hit rateThe share of requests answered from Redis without calling the model.
WorkerA separate process that takes jobs from a queue so the API can reply straight away.
TraceA record of one request: what was retrieved, which tools ran, tokens used, time taken and cost.
Prompt injectionText in the data that tries to give the model new instructions. Treat retrieved text as data, never as orders.

How you actually get the job

Track A: product-based company (main goal)

  1. Pass the online test first. Most product-company screens are DSA plus SQL, so your DSA and SQL practice matters more than any certificate.
  2. Make a target list of 30 companies by week 16: 10 reach, 10 realistic, 10 safe. Include Indian product companies, GCCs of global firms and fintech data teams. Note each careers URL.
  3. Get the project live by week 16. The live AI assistant on top of your own pipeline is your proof that you can build and run it.
  4. From week 16, message 5 engineers or recruiters a week on LinkedIn. Send a 3-line note and your repo link, and ask for a referral only after they reply. Referrals beat cold applications at product companies.
  5. Expect a loop of online test, DSA round, SQL and data modeling round, a backend or AI system design round (for example, design a question-answering service over documents), then hiring manager. Practice each one in your mocks.
  6. Negotiate with a competing offer or your current pay in hand. Ask for the CTC split in writing before you accept.

Track B: remote USD role (next goal, be realistic)

  1. Know the odds. Many US remote roles want US work authorization, several years of experience, or heavy time-zone overlap. With about 1.2 years, a direct remote USD offer is possible but uncommon.
  2. Use the likely route. Move to a strong product company or GCC first, build 2 to 3 years there, then apply remote. This plan makes that first move possible and still lets you try Track B in parallel.
  3. Target remote-first companies that say they hire in India or anywhere. Search Wellfound, Himalayas, We Work Remotely, RemoteOK and LinkedIn with the remote filter, and read each posting for location limits before applying. Many hire through an employer-of-record service such as Deel or Remote.
  4. Build public proof. Keep the repo, README, architecture diagram and demo video polished, and write one short post on what you learned. Remote teams hire on written proof.
  5. Practise async communication. Write clear updates, answer in complete sentences and be ready to work a few hours of US overlap. Include a line on this in your applications.
  6. Protect yourself. Never pay a fee to get a job or to receive equipment, and be wary of offers that skip interviews. Check your EY contract on outside work, and ask a chartered accountant about tax on foreign income before you accept USD pay.

Post template

  1. Problem. What were you trying to do, in two or three sentences?
  2. Approach. What did you build or try? Add one diagram and one short code snippet.
  3. What broke. The bug, the slow query or the wrong answer, and how you found the cause.
  4. Numbers. Before and after results, such as runtime, cost or accuracy.
  5. What I would do differently. Two or three honest lines.
  6. Links. The repo, the relevant folder and the demo.

Aim for 800 to 1,200 words. Do not include anything from EY or any client.

How to add a blog to your portfolio

  1. Keep each post as a Markdown file in your portfolio repo, for example src/posts/airflow-reruns.md, with a title, date, short summary and tags at the top.
  2. Add a Blog page that lists the posts (title, date, summary), and a post page at /blog/post-name.
  3. Render the Markdown with react-markdown, or with MDX if you want React components inside posts. Add code highlighting.
  4. Set a page title, a description and Open Graph tags for each post, so the link shows a proper preview when you share it on LinkedIn.
  5. Deploy the way you deploy your portfolio now, then open each post on your phone to check it.
  6. Share each post on LinkedIn with a two-line summary and the link. Put your blog link at the top of your resume and in your GitHub profile.

Tools: react-markdown and MDX for rendering markdown in a React portfolio.
