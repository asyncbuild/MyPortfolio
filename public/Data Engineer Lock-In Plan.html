The project: GitHub Pulse

GitHub Pulse is a data pipeline plus a chat app. Every day it collects public activity from GitHub (stars, issues and comments), cleans it, organises it into tables, and lets you ask questions in plain English. You can ask which repos are trending this week, or what people complain about in a repo's issues. Every answer links back to its source.

DataGH Archive, a free public record of GitHub events. Nothing from EY and nothing confidential.
Why itIt touches what data engineer job posts list: ingestion, orchestration, Spark, SQL modeling, tests, AWS, then an LLM layer on top, deployed.
Interview line"I built an end-to-end data pipeline on AWS that processes GitHub events and serves a question-answering app, and I measured its accuracy."

What you will have at the end

  • A public GitHub repo with a clear README, an architecture diagram and a tests badge.
  • A pipeline that runs by itself on a schedule in Airflow and recovers from failures.
  • Clean data tables in S3 (Parquet) and analytics tables built with dbt, such as trending repos per day.
  • A live chat page where anyone can ask questions and see answers with source links.
  • An evaluation table in the README: how often the app finds the right source and answers correctly, on 20 questions you wrote.
  • A 2-minute demo video and 3 numbers for your resume: rows processed, runtime, and eval accuracy.

Build it in 11 stages

  1. Set up (weeks 1-2). Create the repo. Run Postgres in Docker. Download 3 to 6 hourly files from GH Archive, load them into a table and write 5 SQL queries.Done when the queries return sensible results and are saved in /sql.
  2. Model it (week 3). Design a star schema: one fact table for events plus tables for repo, actor, date and event type.Done when the fact table has the same row count as the raw table.
  3. Package it (week 4). Turn your loading code into a small Python ETL in Docker, add tests and a CI workflow.Done when GitHub Actions shows a green check.
  4. Move to the cloud (week 5). Create an AWS account safely and write a script that uploads raw files to S3.Done when 7 hourly files sit in S3 and your budget alert is on.
  5. Schedule it (week 6). Wrap the download-and-upload in an Airflow DAG with retries.Done when it runs on a schedule and recovers after a forced failure.
  6. Clean it at scale (week 7). Use PySpark to clean, type and de-duplicate events, write Parquet partitioned by date, and query it in Athena.Done when the Athena row count matches Spark.
  7. Model it for analytics (week 8). Build dbt models for the star schema and a daily trending-repos table, with tests.Done when dbt build passes and you have a lineage graph screenshot.
  8. Make text searchable (week 9). Take issue text, split it into chunks, turn each into an embedding and store it in pgvector.Done when search returns sensible top-5 results for 10 test questions.
  9. Answer questions (week 10). Build a FastAPI /ask endpoint. Count and trend questions go to SQL, discussion questions go to text search. Each answer includes source links.Done when 20 golden questions with correct answers are written down.
  10. Measure it (week 11). Write a script that asks all 20 questions and scores the results. Put the table in the README.Done when the README shows real numbers and one before-and-after fix.
  11. Ship it (week 12). Build the React chat page, deploy the API and the page on AWS, and record a demo.Done when a public URL works on your phone and the video link is in the README.

If you fall behind, finish stages 1 to 7 first. A working pipeline with clean tables is already a strong project. The chat layer can start simple.

Words you will meet

PipelineA chain of steps that moves data from a source to a place where people can use it.
IdempotentRunning a step twice gives the same result as running it once. It makes reruns safe.
ParquetA compact file format for tables. Queries read only the columns they need.
PartitionSplitting data into folders, such as one per date, so queries skip what they do not need.
DAGThe Airflow name for a pipeline: tasks and the order they run in.
EmbeddingA list of numbers that represents the meaning of a piece of text. Similar texts get similar numbers.
RAGFind the most relevant text first, then give it to the model so its answer is based on real sources.
EvalA fixed set of questions with known answers that you re-run to measure quality.

Keep it small, cheap and clean

SizeGH Archive hourly files can be large. Check a file's size before downloading it. Take one hour per day, and keep only three event types early on: WatchEvent (stars), IssuesEvent and IssueCommentEvent.
CostSet an AWS budget alert first. Stop or delete databases and Glue jobs you are not using.
PrivacyEvents contain public usernames. Do not store emails or other personal details, and show aggregated results in your demo.
SecretsKeep AWS keys and API keys in environment variables. Never commit them to the repo.

Why AWS for you

It is where product and startup hiring sits. AWS holds about 32% of the global cloud market and is described as the common choice of startups and tech-forward companies. Those are the employers behind product-based and remote roles.

Azure leans enterprise. It is strongest in Microsoft-heavy enterprises and regulated industries such as banking and insurance. That is a good market, but it is closer to the service-company path you want to leave.

The core skills move with you. SQL, Python, Spark, Airflow, dbt and pipeline design work on any cloud, so picking AWS now costs little if you later land on Azure or GCP.

Source: Data Engineer Academy, AWS vs Azure data engineering. Salary and share figures vary by source, so treat them as rough.

How you actually get the job

Track A: product-based company (main goal)

  1. Pass the online test first. Most product-company screens are DSA plus SQL, so weeks 1 to 17 of DSA and SQL practice matter more than any certificate.
  2. Make a target list of 30 companies by week 12: 10 reach, 10 realistic, 10 safe. Include Indian product companies, GCCs of global firms and fintech data teams. Note each careers URL.
  3. Get the project live by week 12 and the AWS exam booked by week 13. The project proves you can build, and the certificate gets past resume filters.
  4. From week 14, message 5 engineers or recruiters a week on LinkedIn. Send a 3-line note and your repo link, and ask for a referral only after they reply. Referrals beat cold applications at product companies.
  5. Expect a loop of online test, DSA round, SQL and data modeling round, pipeline design round, then hiring manager. Practice each one in your mocks.
  6. Negotiate with a competing offer or your current pay in hand. Ask for the CTC split in writing before you accept.

Track B: remote USD role (next goal, be realistic)

  1. Know the odds. Many US remote roles want US work authorization, several years of experience, or heavy time-zone overlap. With about 1.2 years, a direct remote USD offer is possible but uncommon.
  2. Use the likely route. Move to a strong product company or GCC first, build 2 to 3 years there, then apply remote. This plan makes that first move possible and still lets you try Track B in parallel.
  3. Target remote-first companies that say they hire in India or anywhere. Search Wellfound, Himalayas, We Work Remotely, RemoteOK and LinkedIn with the remote filter, and read each posting for location limits before applying. Many hire through an employer-of-record service such as Deel or Remote.
  4. Build public proof. Keep the repo, README, architecture diagram and demo video polished, and write one short post on what you learned. Remote teams hire on written proof.
  5. Practise async communication. Write clear updates, answer in complete sentences and be ready to work a few hours of US overlap. Include a line on this in your applications.
  6. Protect yourself. Never pay a fee to get a job or to receive equipment, and be wary of offers that skip interviews. Check your EY contract on outside work, and ask a chartered accountant about tax on foreign income before you accept USD pay.

Post template

  1. Problem. What were you trying to do, in two or three sentences?
  2. Approach. What did you build or try? Add one diagram and one short code snippet.
  3. What broke. The bug, the slow query or the wrong answer, and how you found the cause.
  4. Numbers. Before and after results, such as runtime, cost or accuracy.
  5. What I would do differently. Two or three honest lines.
  6. Links. The repo, the relevant folder and the demo.

Aim for 800 to 1,200 words. Do not include anything from EY or any client.

How to add a blog to your portfolio

  1. Keep each post as a Markdown file in your portfolio repo, for example src/posts/airflow-reruns.md, with a title, date, short summary and tags at the top.
  2. Add a Blog page that lists the posts (title, date, summary), and a post page at /blog/post-name.
  3. Render the Markdown with react-markdown, or with MDX if you want React components inside posts. Add code highlighting.
  4. Set a page title, a description and Open Graph tags for each post, so the link shows a proper preview when you share it on LinkedIn.
  5. Deploy the way you deploy your portfolio now, then open each post on your phone to check it.
  6. Share each post on LinkedIn with a two-line summary and the link. Put your blog link at the top of your resume and in your GitHub profile.

Tools: react-markdown and MDX. I have not seen your portfolio code, so these steps assume a React site. If it is plain HTML, write each post as its own page and link them from a Blog page. Send me the stack and I can give exact steps.
